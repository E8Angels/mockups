Implementation notes

This is for the dev plan, not user-facing. Captures the technical questions you raised in the brief.

Where it appears

  • Phase 1: applicant-facing pages only — application form pages and the applicant dashboard (and its tabs: messages, etc.). Render once at the layout level, not per-tab, so it persists across navigation.
  • Mounted into AppLayout (or applicant-only layout wrapper) with a route check; hidden on admin/staff routes.

Email payload sent to support manager

  • From context (auto-attached, not editable): applicant name, email, company name, current page URL, user agent, timestamp.
  • User-supplied: subject, body, file attachments.
  • Send via existing transactional email path; include a Reply-To header set to the applicant's email so support can reply directly.

Screenshot — what's actually possible

Two real options. Neither requires installing anything; both are pure browser APIs.

  • html2canvas (or dom-to-image) — renders the current DOM to a canvas. No permission prompt. Limitations: doesn't capture iframes, cross-origin images may be blank, fidelity is approximate. Best for "good enough" page captures and the only way to capture silently.
  • Screen Capture API (navigator.mediaDevices.getDisplayMedia) — pixel-accurate, captures anything visible including iframes. Requires the browser's permission prompt where the user picks the tab/window. One click, but they have to click through the picker.

Recommendation: ship html2canvas as the default "Take screenshot" button — one click, no prompt, attaches a PNG. It's not perfect but it's invisible to the user. Skip getDisplayMedia for v1; the picker dialog feels heavier than just letting them attach a file from their existing OS screenshot tool (Cmd+Shift+4 etc).

Attachments

  • Standard <input type="file" multiple>. Cap per-file size (e.g. 10MB) and total payload (e.g. 25MB) — match whatever the support inbox accepts.
  • Show name + size chips with remove button. Auto-generated screenshot appears as just another chip in the list.

Backend

  • New route: POST /api/help/contact in routes/. Multipart upload. Pulls signed-in user from session — applicant cannot spoof identity fields.
  • Sends email to a configurable support address (env var, e.g. HELP_SUPPORT_EMAIL).
  • Rate-limit per session (e.g. 5/min) to prevent accidental double-submits or abuse.
  • Optional: also log to a help_requests table for follow-up tracking. Decide later — not needed for v1 if the support manager just works out of their inbox.

Decisions (locked in)

  • Recipient: Support Manager email + friendly name (env var, e.g. HELP_SUPPORT_EMAIL / HELP_SUPPORT_NAME).
  • CC applicant: No. Use Reply-To = applicant's email so support replies land in their inbox naturally.
  • Persistence: Fire-and-forget email. Also log the full payload (subject, body, sender, company, page URL, attachment names/sizes) to the server console at submit time so nothing is lost if email delivery fails.
  • Screenshot: Use html2canvas. After capture, show a thumbnail in the attachment chip — clicking it opens a full-size preview so the applicant sees exactly what's being sent before hitting Send.

Bubble tooltip behavior

  • Hover-only by default (no permanent floating label).
  • Optional: one-time auto-show on the applicant's first session, dismisses after ~4s or on any click. Stored in localStorage so it never shows again.

Page URL

Sent in the email payload but not shown in the user-facing "we'll include" card — keeps the panel clean and avoids confusing applicants with internal-looking paths.
